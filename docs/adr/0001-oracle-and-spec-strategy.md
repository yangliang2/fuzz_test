# ADR-0001: Oracle 分层策略与 spec 渐进沉淀

- 状态：已接受
- 日期：2026-08-29
- 背景调研：`android-fuzzing-research.md`、`kea2-deep-dive.md`、`target-app-selection.md`、`target-app-selection-mega.md`

## 上下文

项目目标：在超大型开源 Android app（首选 DuckDuckGo，备选 Thunderbird/K-9 Mail）上验证三层应用层 fuzzing 路线——Kea2（GUI 层 property-based fuzzing）+ Jazzer（库级 Java/Kotlin fuzzing）+ 静态分析（组件暴露面）。

调研确立的核心事实：GUI 层探索能力早已过剩，**oracle（判定执行对错的机制）才是瓶颈**——崩溃和内存错误有免费 oracle（进程死亡、sanitizer 报警），而业务逻辑 bug 没有任何自动信号。在 AI Coding 场景下，"AI 生成 → 人工全审"的模式不成立，因为代码生产速度使任何全量人工评审都成为瓶颈。

## 决策

### 1. Oracle 按可信度分三层构建，人工审只保留给最后一层

- **第 1 层：通用不变量**（零人工审，全自动信任）：不依赖业务知识、对任何 app 成立的性质——exported 组件收到畸形 Intent 不得崩溃、save→load 往返一致、操作幂等、列表增删一项数量 ±1、旋转/切后台后 UI 状态不丢失。覆盖的正是 AI 高速写代码最易引入的回归类别。
- **第 2 层：从已验证资产转写**（抽查而非全审）：存量测试、数据模型约束（schema/校验逻辑）、git 历史中的 bug fix commit（每个 fix 都是一次 spec 结晶事件，修复前是反例、修复后是正例）。正确性已被历史背书，AI 只做转写，人工只做机械化抽查。
- **第 3 层：AI 自由创作的业务断言**（唯一需要人审的，压到最小）：真正的业务关键规则（钱、权限、数据生命周期）——一个 app 通常只有几十条，审这个子集是可承受的，且本来就该审。

### 2. Property 走"试用期"机制，用运行时数据代替事前人工审

AI 生成的 property 不先审再用，而是先进观察模式跑 N 轮：从未触发 → 自动淘汰；总是违例 → 自动降级；高触发 + 偶发违例 → 才上人审。人工从"全量事前质检员"变为"少量事后仲裁者"。

### 3. AI 的位置是人力放大器，不是裁判

AI 用于：写 property 初稿（Kea2 瓶颈）、写 fuzz harness（Jazzer 瓶颈）、读代码推断组件攻击面（Intent 瓶颈）、崩溃分诊与去重（日常运营瓶颈）——四处全部是"生成后筛选"模式。**不让** AI 替代引擎做探索决策、不直接当 oracle 实时判定（VisionDroid/GPTDroid 一类，复现性与成本过不了 CI 门禁，观望不进主线）。AI Coding 场景下额外锚点：写代码的 AI 同步声明意图，测试侧 AI 拿意图生成 property，实现与意图交叉验证（廉价差分）。

### 4. Spec 不是前置阶段，而是 fuzzing 循环中渐进沉淀的产物

不做"先完整定义业务预期行为再测试"（瀑布陷阱：成本失控、spec 本身未经验证、大部分行为不值得定义）。存量应用的 spec 补充走三路并行：**矿脉挖掘**（约束/测试/fix 历史）→ **观测刻画**（统计不变量，Daikon 思路，作为变更探测器而非正确性裁判）→ **差分锚定**（线上旧版本为事实基准）。防御"把 bug 固化成 spec"：挖出的 property 一律过试用期 + AI 异常嗅探，可疑子集才上人审。

## 后果

- 第一批 property 从第 1 层通用不变量起步，零人工审成本，可立即验证基础设施。
- 人在回路中的位置是"法官"（裁决有争议的少数案件）而非"质检员"（逐件检查），匹配 AI Coding 的吞吐量级。
- spec 与 oracle 互为产物滚雪球：fuzzing 发现的每个问题沉淀为新 property，spec 在真正出过问题的地方自然生长。
- 风险：挖掘类 property 可能固化错误行为（靠试用期 + 嗅探缓解）；第 3 层若业务关键规则数量超预期，人工审成本会回升，届时重审本决策。
